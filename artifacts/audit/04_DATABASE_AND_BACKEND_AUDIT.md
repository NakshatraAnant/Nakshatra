### Migration history
`drizzle/meta/_journal.json`: `0000_init` (1,747 lines, ~120 tables, 100 indexes, 180 FKs), `0001_email_delivery`, `0002_budget_vendor_link`, `0003_social_network` (assessment, circles, games, rituals, referrals; 11 indexes, 10 FKs), `0004_stored_files`. Linear, small, generated by drizzle-kit. Migrations run automatically at every boot (`app.ts:35`).

### Keys, constraints and deletes
- UUID primary keys (`gen_random_uuid()`), composite PKs for join tables (follows, reactions, poll_votes, group_members, game_participants).
- Foreign keys: 162 `ON DELETE CASCADE`, 16 `RESTRICT`, 10 `SET NULL`, 3 `NO ACTION`. Because users are **soft-deleted** (`users.status='deleted'`), cascades almost never fire in practice; deletion is application logic (`account.ts:deleteAccount`).
- Case-insensitive unique indexes on `lower(email)`, `lower(handle)`, `lower(pseudonym)`.
- Idempotency / concurrency uniques: `xp_idem_uq (user, rule, source_key)`, `notifications_dedupe_uq`, `game_submissions_uq (session, round, user)`, `ritual_responses_uq (user, ritual, period, circle_key)`, `referrals_referred_uq`, `circle_invites_token_uq`, payment event ids, idempotency keys on orders/payments/refunds.
- Status columns are free `text` with comments listing allowed values — **no CHECK constraints or enums**. Integrity relies entirely on application code.
- Polymorphic references without FKs: `reports.target_id/target_user_id`, `entitlements.ref_id` (text joined to `products.id::text`), `users.referred_by`, `comments.parent_id`.

### JSON columns (28 `jsonb` in 0000 + more in 0003)
Used appropriately for append-only or computed blobs (chart results, report content, payment payloads, analytics props). Riskier uses:
- `game_sessions.state` holds generated rounds **including server-only secrets**, all reveals and summaries. It is read wholesale by `recentPromptIds()` (30 sessions) and `communityGuesses()`; it grows with every round. Acceptable at this scale; secrets inside a client-adjacent blob are why `publicRound()` must be perfect (it is not — SEC-03).
- `profiles.field_visibility` mixes per-field visibility with unrelated preferences (e.g. `searchHistory: 'off'` read in `account.ts:173`).

## 2. Schema isolation (DATABASE_SCHEMA)

Implementation (`src/server/db/client.ts`):
1. Schema name validated against `^[a-z_][a-z0-9_]{0,62}$` before any interpolation.
2. `migrationsFor()` copies migrations to a temp dir and rewrites `"public".` → `"<schema>".` (drizzle-kit emits FK targets as `"public"."table"`); table/index DDL is unqualified and follows `search_path`.
3. Each pooled connection runs `set search_path to "<schema>"` on `connect` before any other query; failure discards the connection.
4. Migration bookkeeping lives in the same schema (`migrationsSchema`).
5. After migrating: `ENABLE ROW LEVEL SECURITY` on every table in the current schema owned by the app role (no policies → deny for non-owners), and `REVOKE ALL` on the schema, tables, sequences and functions from `PUBLIC`, `anon`, `authenticated`, `service_role`.

Verification:
- `tests/integration/schema-isolation.test.ts` **passes** (PGlite): creates clashing `public.profiles/products/referrals/analytics_events/audit_logs/users` with rows, runs the full app in schema `nakshatra`, and asserts public is untouched.
- **Production: UNABLE TO VERIFY.** The Supabase project `Nakshatra` (ap-southeast-1) is listed as `ACTIVE_HEALTHY` but is hibernated; read-only `list_tables` timed out twice and `get_advisors` reported "currently hibernated". The claim that the **22 legacy public tables** remain unaffected was not checked against the live database. The test covers 6 clashing names, not the actual 22.

Risks noted:
- Raw SQL strings that name tables (`profiles pr` in `social.ts:301`, `assessment_results` in `circles.ts:63` and `play.ts:33`, `blocks b` in `account.ts`) are unqualified and depend on `search_path` — correct given step 3, but any future connection created outside `openDatabase` would resolve them to `public`.
- RLS is defence-in-depth only; the app connects as the table owner, so RLS never applies to it (intended).
- `service_role` normally bypasses RLS on Supabase; the explicit `REVOKE` on the schema is what blocks it. Good.

## 3. Backend data-access patterns

| Pattern | Where | Assessment |
|---|---|---|
| Session lookup on every request | `app.ts:93` → `resolveSession` (join users + roles query) | Runs for static assets and `/uploads` too. 2 queries per request with a pool of 5. **Bottleneck candidate.** |
| In-memory feed ranking | `social.ts:289-331` | Loads ≤400 posts + 6 aggregate queries + 9 hydrate queries per page; offset pagination; fine to low thousands of active users |
| N+1 loops | `circles.ts:39-41`, `social.ts:346,457`, `play.ts:155-158`, `referrals.ts` module GET, `studio.ts communityGuesses` | Grow with activity, not users |
| ILIKE search | `account.ts:146-176` | Sequential scans on profiles/posts/products/events; no trigram/FTS indexes |
| Row locks | game round close, payments webhook, refunds | Correct use of `SELECT … FOR UPDATE` |
| Transactions wrapping side effects | payment webhook generates reports inside the transaction | Causes DEF-01 |
| Counts on hot paths | `circlePoints`, `contributingMembers` (full scans of circle posts/rituals/submissions) | Linear in circle history |

### Index review (selected)
Present and appropriate: `posts(author_id, created_at)`, `posts(created_at)`, `posts(group_id)`, `comments(post_id, created_at)`, `notifications(user_id, created_at)`, `analytics(name, created_at)` and `(user_id, created_at)`, `audit(actor_id)`, `xp(user_id, created_at)`, `game_sessions(circle_id, created_at)`, `ritual_responses(ritual, period, circle)`.

Missing or weak (estimates, not measured):
- `blocks(blocked_id)` and `mutes(muted_id)` — `blockedSet()` filters `blocker_id = X OR blocked_id = X`; the second branch has no index.
- `posts(group_id, created_at)` composite for circle feeds (`group_id` alone exists).
- `posts(visibility, created_at)` / partial index for public feed candidates.
- `reports(target_type, target_id, status)` — feed counts open reports per post id.
- `comments(author_id)` — achievements and deletion filter on it.
- `game_sessions(status, updated_at)` — abandonment check is per-load, so not needed yet.
- Login throttle counts `audit_logs` by `(actor_id, action, created_at)`; only `actor_id` is indexed — acceptable while audit volume is small.

### Connection pooling
`DATABASE_POOL_MAX` default 10; Render blueprint sets **5** to fit Supabase's free session pooler. With per-request session lookups, a page load that fetches 10–20 static assets plus 3–6 API calls uses the pool heavily; requests queue rather than fail, which shows up as latency.

## 4. Data lifecycle

| Data | Created | Retained | On account deletion |
|---|---|---|---|
| Account (`users`) | signup | forever (soft delete) | email replaced, password disabled, status `deleted` |
| Profile | signup | forever | pseudonymised (`deleted-xxxx`, "Deleted user") |
| Sessions | login | **never purged** (expired rows remain) | deleted |
| Auth tokens | verify/reset | never purged | cascade not triggered (soft delete) |
| Email outbox (contains links) | every email | **never purged** | not deleted |
| Personality answers/results | assessment | forever, full history | deleted |
| Birth data, charts | Cosmic ID | until consent withdrawn | deleted |
| Posts/comments | user | soft-deleted only | bodies blanked, soft-deleted |
| Game submissions | play | forever | payload blanked, withdrawn |
| Ritual responses | rituals | forever | deleted |
| Circle membership | invite | until leave | removed; owned circles archived (members lose access) |
| Uploads / stored files (avatars, post images, verification selfies) | upload | forever | **not deleted** |
| Analytics events | every action | **unbounded**, keyed by user id | **user id retained** |
| Audit logs | security actions | unbounded | actor id retained |
| Orders/payments/refunds | commerce | forever (accounting) | retained (documented) |
| Referrals, XP | activity | forever | retained |
| Search history | every search (default on) | unbounded (last 20 shown) | deleted |

There is no retention job for any table. Growth is unbounded for `analytics_events`, `audit_logs`, `notifications`, `email_outbox`, `sessions`, `search_history` and (with `STORAGE_DRIVER=database`) `stored_files` bytea — which counts against Supabase's free 500 MB database quota.

## 6. Verdict
The schema is normalised, consistently keyed, and protected by unique indexes where concurrency matters. Its problems are **breadth** (82 tables outside the product), **no CHECK constraints**, **no retention**, and a few hot paths that will need indexes or restructuring before ~10k active users. Production isolation is well engineered in code and tested on PGlite, but its live state is unverified.
